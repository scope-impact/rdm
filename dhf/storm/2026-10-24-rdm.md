# Event storm: RDM, first version

The first event storm on RDM itself, run on 2026-10-24 as a simulation (one
agent playing domain expert, developer and facilitator). Its scope is the first
version in `dhf/decisions/adr-0002-spec-first-regeneration.md`: the regulated
profile and the graph are out.

This board is a working product, not part of the spec. What it decided is in
`dhf/spec/needs.edn`, `dhf/spec/events.edn` and `dhf/spec/model.edn`; what it
could not decide is under [Hotspots](#hotspots).

**Inputs read:** the ADR; `dhf/harness/spec.feature`; today's user needs
(`dhf/documents/verification_and_validation_plan.md`); the CLI
(`docs/reference/cli.md`); the bounded contexts of today's record
(`dhf/documents/architecture.md`); Löyly's `README.md` and `harness/README.md`
(`skallinen/loyly`).

## Actors

| Actor | Kind | Wants |
|---|---|---|
| Engineer | person | to say what the product does, once, and have everything else follow from it |
| Reviewer | person | to approve a spec change knowing what it changes |
| Spec owner | person | to know how much of the product the spec really carries |
| Coding agent | external system | a clean room and a spec, nothing else |
| Test runner | external system | to run step definitions in its own stack and report |
| Git host | external system | holds merges and pull requests |

*Later decided:* every role is filled by a human or an agent. The coding agent
became the **Builder** role, beside engineer, reviewer and spec owner (ADR 0002,
"Roles").

## Aggregates

An aggregate is what must be checked together, in one step, for its rules to
hold.

| Aggregate | Commands | Invariants it protects |
|---|---|---|
| **Ledger** | Stamp spec | An id is issued once, ever; the highest issued only grows |
| **Spec revision** | Parse spec, Gate spec | One id per scenario, unique ids, one level, a known need, the declared Gherkin subset |
| **Model** | Lint model, Generate views | The C4 lint rules; one container per bounded context; every event named is declared; every component owns a feature file and every feature file has an owner |
| **Cut** | Cut spec | Only a merge on the default branch; N is one more than the last |
| **Clean room** | Build clean room | Built only from a cut; every fenced path matched, and absent from tree and history |
| **Ratification** | Ratify build | Port free; boot within budget; results written; identity proved; step definitions black box |
| **Run verification** | Derive status | Every stamped scenario gets a status; an empty or unreadable input is named, never skipped |
| **Cycle** | Score cycle | Nothing measured, nothing filed; unverified counts as failed |
| **Project skeleton** | Init, Adopt | Never overwrite an existing file |

## Bounded contexts

The aggregates group into eight contexts, each its own runnable container
(ADR 0002), plus the repository as the one store.

| Context / container | Aggregates | Its language |
|---|---|---|
| project | Project skeleton | project, skeleton, hook, task |
| specification (`spec`) | Ledger, Spec revision | scenario, id, ledger, level, need, planned |
| architecture | Model | model, view, container, component, event |
| verification | Run verification | result, verified, failed, unverified, trace, release |
| regeneration | Cut, Clean room | cut, fence, clean room, fenced path |
| ratification | Ratification | gate, boot budget, identity, black box |
| measurement | Cycle | checklist, cycle, score, scoreboard, denominator |
| publishing | (none: read models only) | site, page |

**Why this cut.**

- **Ratification and measurement are separate on purpose.** Ratification feeds
  the coding agent (it may iterate against it); measurement reports to a
  person and never into the loop (Löyly's harness/instrument split). In one
  container the scoreboard would sit next to something the agent talks to.
- **Regeneration is separate from ratification**: what goes into a clean room
  (the cut, the fence) is decided before the agent starts; what is judged
  after. One custody boundary each.
- **Specification and architecture are separate**, joined by `SpecParsed`:
  the model owns the spec through file paths, and the check that every
  component owns a feature file is the model's invariant, not the spec's.

**Rejected.**

- *One "harness" container for cut, fence, gate and score.* That is how Löyly
  ships it, as files in one directory, but it merges the two custody
  boundaries above.
- *Status inside measurement.* Status is needed day to day (the release
  check, the site); measurement is per cycle and for one person.
- *Publishing inside verification.* Publishing reads three contexts; putting
  it in any one of them makes the other two its upstream for no reason.

## Views (preview)

The model was rendered once with a throwaway generator (not committed: views
are generated by the architecture container once it exists) and `mmdr` 0.3.1,
and the renders were inspected. Two findings, both folded back:

- **A person's or system's name is drawn over its description once the
  description wraps past two lines.** Descriptions were cut to under about 45
  characters, and the lint gains a length rule (`@spec-0009`).
- **One container view with every relationship was unreadable**: 13 elements
  and about 30 arrows. It is split by viewpoint, as the C4 skill advises, into
  three views over the same model: the events between containers, the people
  and systems using them, and their reads and writes of the repository
  (`:show` in `model.edn`).

`mmdr` still places some relationship labels away from their arrows in the
denser views. That is what the render check (`@spec-0016`) exists to catch,
and it is H13 below.

## After the first review

An independent review (a subagent, 2026-10-24) asked for changes: the public
surface was undefined, ratification assumed a server, the fence failed on its
own configuration and let today's implementation into the clean room, and the
judge and the cycle record were undefined. The owner's answer was to keep it
simple, and the spec now says:

- **One command, `rdm-spec <task>`**, installed once; no task file per project.
- **Boot and Identity are gone**: rdm-spec is a command, not a server.
- **The clean room is an allow-list**, so nothing reaches it by being forgotten,
  and it carries no source checkout.
- **No pinned judge**: the installed rdm-spec ratifies and scores, never the
  build under test (this revises H7).
- **The bus is design, not requirement**: its scenarios are what a black box can
  see (the events a run prints).
- **Regeneration has a scope**: the project, one container or one component.

## After the second review

A second independent review asked for changes again. Compared with Löyly, the
owner kept it simple:

- **A modular monolith.** One container, the `rdm-spec` command; the bounded
  contexts are composable modules, drawn as boundaries. Composable means each
  can be regenerated alone while the others stand.
- **Ratify trusts only the cut**: only the room's implementation comes back,
  into a fresh checkout of the cut, as Löyly ratifies `impl/` in its trusted
  repository. Step definitions run the build's own entry point.
- **Events only within one run.** The five events between steps that run at
  different times are gone; those steps meet through files, as Löyly's do.
- **No code-boundary lint, no render check**; the code layout is configuration;
  the very first cycle is a marked bootstrap.
