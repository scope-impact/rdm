## Question

Does `MEASURE_EFFECT` reference `PROBABILITY_OF_HARM` (one specific harm pathway) or `HAZARDOUS_SITUATION` (the situation as a whole)? The source model flags this as its own open question and notes retrofitting either direction is painful.

## Evidence

**Correction to this ticket as first written.** It originally argued from the location-permission control appearing on RISK-NET-002 and RISK-SAFETY-005 as "one mechanism, opposite valence, two harms, one situation". Re-read against the register, all three parts of that are wrong:

- The valence is the **same**. "Declining the location permission disables only these cards" is listed as a *control* on both risks — no card means nothing to over-rely on, so declining mitigates the safety risk too.
- The two risks do **not** share a hazardous situation. NET-002 situation is a user granting the permission and each lookup revealing coarse location and IP; SAFETY-005 situation is a user treating the alert card as their emergency notification channel. They share a *feature*, not a situation.
- So the case is evidence for **MEASURE reuse** — one mechanism, two risks, different residuals (Low and Medium) — and says nothing directly about effect granularity.

**What the estate actually shows.** Measured across all 34 scored risks (20 halla-health-infra, 14 halla-health wallet): **34 distinct hazardous situations, and zero pairs sharing one** — no pair reaches even 0.40 token overlap on the situation text. Every situation in current practice has exactly **one** harm.

That is the crux. Where a situation has one harm, `PROBABILITY_OF_HARM` granularity and `HAZARDOUS_SITUATION` granularity are **isomorphic** — the two options are indistinguishable on every row that exists today. The choice only bites the first time a situation carries a second harm.

Note also what the source model warning is actually about: it cautions against collapsing `PROBABILITY_OF_HARM` into *columns on the situation*, which is a different thing from choosing situation-level granularity for `MEASURE_EFFECT`.

## What has to be decided

Whether one-situation-many-harms is a modelling goal being aimed at, or whether 1:1 is a true description of the domain. If it is a goal, harm-pathway granularity is the only non-lossy choice and the row cost is accepted up front. If 1:1 holds, situation-level granularity matches how registers are actually authored, and the extra table is unexercised structure. Either way the decision needs stating, because it is not currently derivable from the data.

## Implementation Notes

RESOLVED. Recorded as [decision-001](../decisions/decision-001%20-%20Mitigation-effects-attach-to-the-harm-pathway-not-the-hazardous-situation.md).

**`MEASURE_EFFECT` references `PROBABILITY_OF_HARM`** — harm-pathway granularity.

Decided on intent, not on evidence, and the record says so. Measured across all 34 scored risks (20 infra, 14 wallet): 34 distinct hazardous situations, zero pairs sharing one, no pair reaching even 0.40 token overlap. Every situation in current practice carries exactly one harm, which makes the two options **isomorphic on every row that exists today**. 1:1 was judged "maybe not the honest" description of the domain, so the current shape is under-modelling and harm-pathway is the only non-lossy choice.

**The rest of the tree, as settled:**

- **One `MEASURE`, several `MEASURE_EFFECT` rows** where a mitigation bears on more than one pathway — never a duplicated measure per risk. 8 of 14 wallet risks already restate a mitigation from elsewhere in different words, 4 pairs being the same mechanism written twice.
- **Effects are derived, with explicit override.** The projection emits one effect per (measure, pathway) pair from where the control already sits; an inline annotation is only needed to override the default of "reduces this pathway, unquantified". Requiring an annotation on all 160 controls in the estate is where register-writing stops.
- **Effects are reducing-or-neutral, never signed.** An aggravating consequence is a different hazard and is recorded as its own risk, so the register cannot silently net two harms against each other. Noted for the record that no aggravating case was found: the location-permission control this ticket originally cited turned out to be mitigating on both risks.
- **An effect targets `p1_level` or `p2_level`, never severity.** Severity is a property of the harm, so a measure that changes it is changing which harm can occur — a different pathway. `p2_level` is optional; requiring it would force 34 re-scorings before anything works.
- **Recorded residuals are provisional**, recomputed rather than backfilled to fit.
- **Canonical term is `MEASURE`** in the model and the schema; "Controls" stays as the markdown heading, and `risk_controls` is the table to rename. Both words are legitimate under ISO 14971 ("risk control measure"), so the register heading should not churn for the schema. Recorded in the new root [CONTEXT.md](../../CONTEXT.md).

**Ruled out of scope:** re-modelling the 34 under-modelled risks so situations carry their several harms. Real work, but on halla-health, not rdm — recorded in the map Out of scope.
