## Question

If types and attributes become rows rather than classes, their identifiers become data that has to stay stable across renames, re-exports and merges. A Pydantic class gets this free from the class name; a row does not.

Surfaced by the ReqIF/StrictDoc research (RDM-004.05), which found this is where both reference implementations are weakest:

- ReqIF binds an instance `AttributeValue` to its `AttributeDefinition` by **identifier, never by name**, so the identifier is load-bearing — and the schema declares no `xsd:key`/`xsd:keyref` at all (verified: count is 0), so nothing enforces that the reference resolves.
- StrictDoc **regenerates every type, attribute and enum identifier on each ReqIF export**: two exports of identical input differ on 94 of 201 lines. Round-tripping therefore does not preserve identity.
- StrictDoc web-UI grammar edits track renames by a field MID but silently drop removed fields and unregistered relations.

Decide what identity means for an `ITEM_TYPE` and an `ATTRIBUTE_DEF` in a markdown-first source: whether the identifier is the frontmatter key name, an explicit stable id, or content-derived; what happens on rename; and what guarantees a re-export or a merge must preserve. Blocked on how far types become data at all — if they stay classes, this is moot.
