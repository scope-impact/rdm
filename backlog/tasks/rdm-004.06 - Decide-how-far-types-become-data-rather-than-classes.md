## Question

The source model calls per-project types "the biggest structural difference from a conventional issue tracker and it is not optional". rdm today does the opposite: `RiskDoc`, `Task`, `Milestone`, `Decision` and `AcceptanceCriterion` are Pydantic classes with one DuckDB table each (`risks`, `tasks`, `milestones`, `decisions`, `acceptance_criteria`).

Measured pressure for the change: halla-health-infra alone already carries 9 distinct item types and 64 attribute definitions, every one emergent from markdown frontmatter and none declared anywhere — which is how 25 of 128 backlog tasks came to use `HH-INFRA-nnn` against the repo own documented lowercase convention with nothing catching it.

Decide how far to go: keep classes and add a declared-schema validation layer over frontmatter; move to generic `ITEM`/`ATTRIBUTE_VALUE` tables with types as rows; or a hybrid where the spine is generic and hot types keep a projection. Include what happens to the existing five tables and their migration.
