## Question

How do ReqIF and StrictDoc actually represent per-project types and attributes, and what does each pay for it?

Needed to inform the decision on how far `ITEM_TYPE`/`ATTRIBUTE_DEF` should replace rdm Pydantic classes. Specifically: ReqIF `SpecType`/`AttributeDefinition`/`DatatypeDefinition` — how datatypes and enumerations are declared and how tools validate instances against them; StrictDoc "grammar" — how a per-document grammar is declared, what validation it gives, and how it exports to ReqIF; and for both, how a *typed* model is queried without the type being a class.

Capture findings on a throwaway research branch and link from this ticket. Do not propose an rdm design; that is the dependent ticket.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Resolved. Findings: [docs/research/reqif-strictdoc-typing.md](../../docs/research/reqif-strictdoc-typing.md) (679 lines, each claim tagged with the primary source that owns it).

**1. ReqIF.** Four layers: a shared `DatatypeDefinition`, an `AttributeDefinition` contained by exactly one `SpecType`, and an instance `AttributeValue` bound to its definition by **identifier, never by name**. 21 classes express 7 datatypes; enumerations are first-class objects with per-value identity, and `LONG-NAME` is only a label. **`AttributeDefinition` has no required flag — mandatory-ness is not expressible in ReqIF.**

**2. StrictDoc.** Per-document `[GRAMMAR]` (textX), shareable via `.sgra`, config alias or `.gra.md`. Only four field types (String, SingleChoice, MultipleChoice, Tag) — no numeric, date or boolean — but it does have `REQUIRED`, closed enumerations, declared relations, and field order as part of the type. Grammar change has no migration path: a hand-edited file simply fails to parse, while a web-UI edit destructively rewrites every node and silently drops removed fields and unregistered relations. ReqIF export loses `REQUIRED` entirely, raises `NotImplementedError` for `Tag`, and regenerates every type/attribute/enum id per export.

**3. Querying.** **No prior art to copy.** ReqIF has no query surface; both implementations use id-keyed hash maps for dereferencing and linear scans for everything else. StrictDoc has a real query language, but there is no way to name a custom node type — `node.is_requirement` is hardcoded to `node_type == "REQUIREMENT"`, so a custom `RISK` node is invisible to StrictDoc own queries. Its graph DB has no type index and no attribute-value index.

**What this changes for the dependent decision (RDM-004.06):**

- The ticket presupposed that tools validate instances against a type. At the ReqIF interchange layer essentially none do — a `SpecObjectType` is a labelling and presentation contract, not a validation contract. Verified independently against the normative XSD: all 64 `REQUIRED` occurrences are `use="required"` on XML attributes, and `xsd:key`/`xsd:keyref` count is **0**, so the schema expresses no referential integrity. Four deliberate type violations passed `reqif validate --use-reqif-schema` with zero errors.
- StrictDoc validates **more** than ReqIF, via a hand-written validator — and all of it is lost on ReqIF export. So borrowing ReqIF names buys interchange and zero validation; the validation layer is ours to build either way.
- Identifier stability becomes a first-class problem that Pydantic classes get free from the class name. Raised as its own ticket.

**Source gap, stated because it bounds one claim.** `www.omg.org` and both mirrors of the specification PDF are blocked by this environment egress proxy, so the specification *prose* was not read. Claims about what the model *is* rest on the normative XSD and the Eclipse RMF reference metamodel and are solid. The claim that the spec does not *mandate* instance/type validation is argued, not quoted: every artefact that would carry such a MUST is silent. RMF constraint ids `C1.1`-`C1.9` point at a numbered catalogue in the separate ReqIF Implementation Guide, also unreachable — that is the first thing to read when omg.org is available, and it could soften this one claim.

`mkdocs build --strict` verified passing with the new page (exit 0; deliberately left out of nav, reported at INFO level only).
