    Computer software validation — RDM¶

    Id: CSV-001 · Status: proposed · References: VVP-001, DC-001, SDS-SYS-001 · Kind: risk · Download as PDF

    Proposed, not yet approved. The validation of RDM as a tool: software used as part of a regulated team's quality management system, not a medical device, validated the computer software assurance way, risk based ([[13485:4.1.6-procedure]]). This is RDM's final document: its intended use, its architecture, its risk analysis (the risk policy and the risks are this document's frontmatter, which the release gate evaluates), its whole spec with each requirement's verification, the assurance, the record and change. It is a template: rdm render fills in the architecture and the spec from the record, with the include and glob filters, and the verification from data/verification.yml. A team that adopts RDM validates it for its own intended use; this record is the supplier's assurance it can rely on.

    Intended use¶

    RDM reads a team's spec, checklists, risks, documents and executed test results; reports the checklist clauses no document references (gap analysis); decides whether a release may go ahead (the release gate); and generates the verification report and the evidence bundle, which are quality records. It is used directly as part of the quality management system: it automates a quality process (the release decision) and maintains quality records ([[CSA:intended-use]]). It does not produce the product itself, so ISO 13485 7.5.6 applies to it only where a team uses its gates inside production.

    System Architecture¶

    RDM audits the record of regulated software. It reads a spec as Gherkin (each scenario tagged with an id a requirement), takes the evidence of each requirement from Allure test runs, checks documents against the checklists of the standards that apply, decides whether a release may go ahead, renders regulatory documents, and builds it all into a read-only graph that people and agents query. It never authors the spec (ADR 0002).

    This document holds design only: RDM's own requirements and user needs are its spec, written the Löyly way in .pi/ (a slice of .pi/plan/ per bounded context), read like any project's.

    The four parts¶

    Part Responsibility Writes to the record?
    Record read the record: the spec (Gherkin), the risk register, validation records, checklists, test results, git scaffolding only (init, adopt); every other change is a reviewed commit
    Gates pass/block decisions on the record no
    Graph the knowledge graph: the record as RDF, queried and validated; agents read it over MCP (rdm graph mcp) no — rebuilt from the record, never edited
    Documents regulatory documents rendered from the record no

    Only people and agents change the record, and only through a reviewed pull request; the merge is the approval. Nothing RDM derives (graph, matrix, documents, evidence bundle) is edited by hand or fed back into the record.

    System context¶

    Who uses RDM: a regulatory author renders documents and checks them against checklists; a team runs the gates in CI on every change; an agent reads the record through the graph's MCP server; a reviewer reads the verification report and the evidence bundle. RDM runs as the rdm command, as a pytest plugin inside a project's acceptance run, and as reusable CI (a GitHub workflow and actions). It depends on git, on Allure results written by the project's test runner, and, to render PDFs, on Pandoc and Typst.

    Dependency rule¶

    A context imports only contexts of a lower layer, and the shared kernel; nothing imports a context of the top layer. The layers and each context's code are in the frontmatter, and a test fails on any import that breaks the rule, and on any module no context's code holds (tests/dependency_rule_test.py).

     5  publishing · graph              read models: read every context, feed none back
 4  release                         decides: verified status, risk and validation → release
 3  test_evidence                   translates Allure results into runs of the spec's requirements
 2  specification                   the core: the spec read as Gherkin, needs, requirements
 1  risk · compliance               leaves: their own languages, nothing but the kernel

    The leaves sit below the core because the core uses them and they use nothing: the release gate applies the risk rules, and neither leaf reads a requirement. The evidence bundle renders the matrix and the verification report, so it is publishing's, and realises release's item-04-003.

    Flow¶

    The spec → its evidence (Allure runs) and its risks → the release gate decides, and gap analysis holds the documents to their checklists → the knowledge graph and the documents are derived from the same record. Agent skills (how to author requirements, test-first, risk analysis) are maintained outside RDM, in scope-impact/agent-skills. RDM ships no planning tooling: tasks and issues live in their own tools, outside the record (see docs/about/plan-vs-record.md).

    Not yet in scope¶

    In rough order: turning a regulation into a checklist mapped to its standard's clauses; pushing the graph to an external RDF store, with the vocabulary and gate shapes versioned; and several projects in one graph (clause identifiers are already project-independent). Each enters through a user need and requirements in the spec before any code.

    Process risk¶

    A failure of RDM to perform as intended could let a release go ahead with a requirement not verified, a risk not evaluated, or evidence that does not describe what was tested: RDM determines acceptability with limited additional human review where a team relies on its gate alone. That is a quality problem that could foreseeably compromise safety: high process risk ([[CSA:risk]], [[13485:4.1.6-proportionate]]). The ways it could fail are the risks below, evaluated against the risk policy below (severity from the harm, probability from the situation, the residual after the controls), each control a requirement of RDM's own spec. The analysis covers every factor the guidance names (its §V.A(2)), for failures that are reasonably foreseeable, not only likely:

    Factor Risks
    Configuration and management RISK-TOOL-008 (the spec read short)
    Security RISK-TOOL-004, RISK-TOOL-006, RISK-TOOL-007
    Data integrity RISK-TOOL-002, RISK-TOOL-005
    Data storage RISK-TOOL-009 (evidence not retrievable)
    Data transfer, operation error RISK-TOOL-010 (a decision on other results)

    Specification¶

    RDM's spec, written the Löyly way in .pi/spec/: each accepted scenario, a concrete Given/When/Then example stamped @item-NN-SSS, is a requirement, verified by the acceptance test that claims it; each event-model screen, linked to its Allium surface, is a user need. The table is each requirement's verification from the executed results; the feature files follow, laid out by the gherkin render filter.

    The spec was written after RDM's code, to describe it, so for this revision only the Gherkin is held to the code, by the tests that claim it; the Allium surfaces and event models are held to it by review. From the next change on, RDM is built the Löyly way, spec first and then regenerated, so the code cannot drift from any part of the spec.

    item-05-001 ✓ verified · 1 run Gap analysis names each missing reference and exits non-zero when one is missing or nothing was checked

    Given a checklist "cl.txt" with the clauses X-1 and X-2

    Then it exits 3, listing X-2 and not X-1, under the heading "# 1 gap:"

    And a stray "[[" does not turn the next paragraphs' mentions into references: X-2 is still missing
    And a bare mention "We do not address X-2" is no reference to X-2: it exits 3
    And [[X-12]] does not reference the key X-1: it exits 3
    And [[FDA-SW:sdmp: This document is a pointer document.]] references the key FDA-SW:sdmp: it exits 0
    And [[FDA-SW:sdmp]] does not reference the key FDA-SW: it exits 3
    And a byte-order mark is not part of the first key: a checklist beginning with a byte-order mark before "X-1 first" is covered by full.md
    And "include cl.txt " with spaces around the name is resolved
    When nothing could be checked: a checklist with no clauses, a checklist that does not exist, a bare "include", an include of a file that does not exist, a document that does not exist, or a directory given as a document
    Then it exits 2, never 0
    When a document covering every clause still holds a "TODO: write this section" placeholder
    Then it exits 0 and warns, naming the document and its placeholder
    When its report of 20000 gaps is piped into a reader that stops after one line
    Then it ends quietly, with no traceback and no BrokenPipe error

    The accepted scenarios of this context: the risk register kept in the record, each risk scored only against the risk policy the project declares, each control a requirement of the spec, and the release held back while a risk is unscored, uncontrolled, or residually unacceptable without a named acceptance.     Assurance activities¶

    Proportionate to that risk ([[CSA:assurance]]):

    • Scripted, automated testing. Each of RDM's 44 requirements (stamped Given/When/Then scenarios in .pi/spec/) is verified by an acceptance test that claims it; RDM's own release gate blocks while any requirement lacks a passing run, any user need is unaddressed, or any risk control is unverified.
    • Risk-based focus. The requirements that control one of the risks (the release gate, the read-only agent server, the served graph) count only once verified and the risk's residual is evaluated again.
    • Scenario testing on a real product. The worked example runs RDM's gates over Löyly's pi harness (201 requirements, six clojure.test suites, a spec in another repository) on every change to RDM, beside RDM's own record.
    • Ongoing monitoring. Every change runs every gate in CI, on RDM's own record (dogfooding) and on the example; a gate that stops passing stops the change.

    The assurance also relies on ([[CSA:assurance-considerations]]): the dependencies pinned in uv.lock, the RDM container image built from them, and the executed results RDM keeps as evidence rather than screenshots.

    Record¶

    The record of each validation ([[CSA:record]], [[13485:4.1.6-records]]) is the evidence bundle the design-controls workflow writes from each run: the verification report (the commit validated, who and what ran the tests and where, each requirement with its runs, the issues found, and whether the evidence is release-grade), the traceability matrix, the verification data and the results with a manifest and one SHA-256 over them. The conclusion is the release gate's verdict; the approval, the reviewed pull request.

    The record system and Part 11¶

    The validation record is required as evidence of a validated state and is kept electronically, so it is a Part 11 electronic record and the system that keeps it is held to Part 11 ([[CSA:part11]]): git as the document control system, GitHub as its service provider and RDM's gates, mapped control by control in DC-001. That system is validated by this same procedure: RDM's gates are what the assurance above tests.

    Change¶

    RDM is validated before a release is first used and again after every change ([[13485:4.1.6-before-use]], [[CSA:change]]): every pull request runs every gate before it can merge; a release is a tag, and a team adopting RDM pins its CI to one release (the reusable workflow and the image, item-04-004), so a new RDM release reaches a team only when it changes the pin, and the team assesses that change for its own use ([[13485:7.5.6-software]] where RDM is used in production).
