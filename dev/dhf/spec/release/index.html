    Spec — release¶

    Slice 04-release of RDM's spec, written the Löyly way in .pi/spec/release/, read as the release gate reads it. Each user need is a screen of the event model, linked to its Allium surface; each accepted scenario, stamped with an id, is a requirement.

    User needs¶

    release/release-blocked¶

    A release is blocked until every requirement of the spec is verified by a passing test.

    • Surface: ReleaseGateDesk
    • Facing: ReleaseManager
    • Rules: ReleaseGate
    • Event storm: Release gate passed (Release manager, or CI); Release blocked (Release manager, or CI)

    release/release-evidence¶

    A release's evidence (verification data, traceability matrix, verification report) and the device-master-record index can be produced as retained, generated artifacts from the record.

    • Surface: ReleaseEvidence
    • Facing: ReleaseManager
    • Rules: EvidenceBundle
    • Guarantees: DmrIndexFromFrontmatter, VerificationReportForAReviewer
    • Event storm: Evidence bundle written (Release manager, or CI)

    release/trace-verification¶

    Each requirement's verification status is traceable from executed test results.

    • Surface: TraceVerification
    • Facing: RegulatoryAuthor
    • Rules: Verify
    • Guarantees: RunLabelledWithTheCommitUnderTest, RunRecordsWhoRanItAndWhere, SpecNeedsReadFromTheirSource, UnreadableResultNeverPasses
    • Event storm: Verification recorded (Regulatory author, or CI)

    spec.feature 
    Feature: Release
  The accepted scenarios of this context: what holds a release back, how a
  requirement's status is traced from executed results, what a release
  retains, and RDM's gates for other repositories' CI. Each is stamped with
  an item id that is never renumbered or reused, and verified by the
  acceptance tests whose Allure results carry that id as a tag label.

  Rule: A release is blocked until the spec is read whole and every requirement has a passing run

    # release.allium, rule ReleaseGate (requires 1 to 6)
    @allium-rule-success.ReleaseGate @allium-rule-failure.ReleaseGate.1 @allium-rule-failure.ReleaseGate.2
    @allium-rule-failure.ReleaseGate.3 @allium-rule-failure.ReleaseGate.4 @allium-rule-failure.ReleaseGate.5
    @allium-rule-failure.ReleaseGate.6
    @item-04-001
    Scenario: The release gate passes only when every requirement has a passing run and none fails
      Given a spec whose feature file stamps item-01-001 and item-01-002, both addressing the need Release
      When the release manager runs the release gate with no Allure results
      Then release is blocked, item-01-001 and item-01-002 untested
      When a passing run tagged item-01-001 is added
      Then release is blocked, naming item-01-002 and not item-01-001
      When a failing run tagged item-01-002 is added
      Then release is blocked: item-01-002 failed
      When item-01-002's run passes and a failing run tagged item-01-001 is added
      Then release is blocked, naming item-01-001: one passing run does not outweigh a failing one
      When the failing run of item-01-001 is removed
      Then release passes
      When an unstamped scenario "an unstamped behaviour" is added to the feature file
      Then release is blocked, naming "an unstamped behaviour"
      When a second scenario is stamped item-01-001 instead
      Then release is blocked: item-01-001 is stamped twice
      When a feature file "broken.feature" that Gherkin cannot parse is added instead
      Then release is blocked, naming broken.feature
      And a slice of a Löyly plan whose spec.feature is missing (a link to a folder git never received) blocks release, naming the slice
      When the feature file holds no stamped scenario
      Then release is blocked: there is nothing to verify
      And a repository with no spec at all is blocked: no spec was found

  Rule: Each requirement's status is reconciled from the tag labels of executed Allure results

    # release.allium, rule Verify
    @allium-rule-success.Verify
    @item-04-002
    Scenario: Verified, failed and untested come from the runs that carry each requirement's id
      Given Allure results: run p passed tagged item-01-001, run f failed tagged item-01-002, run s skipped tagged item-01-003, run b broken tagged item-01-004
      When the requirements item-01-001 to item-01-005 are reconciled against them
      Then item-01-001 is verified
      And item-01-002 and item-01-004 have failed
      And item-01-003 and item-01-005 are untested
      When a failing run names item-01-001 only as its story, feature and epic labels
      Then item-01-001 is still verified: only a tag label claims a requirement
      When a passing run carries the tag label "@item-01-005"
      Then item-01-005 is verified: the "@" before the id is read
      When item-01-001 to item-01-003 address the need Release, item-01-004 and item-01-005 the need Trace, and verify writes the verification data
      Then the traceability matrix rendered from it shows each requirement's status under the need it addresses

  Rule: A release's evidence is retained as one bundle, generated from the record, never mixed with an earlier one

    # release.allium, rule EvidenceBundle (requires 1 to 2)
    @allium-rule-success.EvidenceBundle @allium-rule-failure.EvidenceBundle.1 @allium-rule-failure.EvidenceBundle.2
    @item-04-003
    Scenario: The evidence bundle holds the verification data, the rendered matrix, the report and the results
      Given a record with a spec, a traceability matrix template and Allure results with attachments and a container
      When the release manager writes the evidence bundle to an output directory apart from the results
      Then the bundle holds the verification data computed from the executed results
      And the traceability matrix rendered from it, with no template markers left
      And the executed results with every attachment and container they reference
      And the verification report, or the manifest says why it is not there
      And a manifest listing exactly the files bundled
      And a symbolic link among the results is not followed, and a missing attachment is listed in the manifest
      And an unreadable result is named in the manifest
      When the bundle is written again over the earlier one
      Then its results replace the earlier bundle's, never mixed with them
      When the output directory would hold the results or sit inside them
      Then the bundle is refused and the results are left untouched
      When the record has no traceability matrix template
      Then the bundle is refused, naming the missing template, and no bundle is written

    allium/release.allium 
    -- allium: 3
-- .pi/spec/release/allium/release.allium
--
-- Scope: the release context: whether a commit may be released (the release gate), each
-- requirement's verification status from executed Allure results (verify), and the
-- retained evidence of a release (the evidence bundle). The surfaces are the needs this
-- context is home to: release-blocked, trace-verification, release-evidence
-- (event-model/area.edn).

------------------------------------------------------------
-- External Entities
------------------------------------------------------------

-- The spec RDM reads (specification): its requirements and the needs they address.
external entity Spec {}

-- One executed test run, read from an Allure result (test_evidence).
external entity TestRun {}

-- The person who releases a version of the product.
external entity ReleaseManagerAccount {}

-- The person who keeps the record.
external entity AuthorAccount {}

------------------------------------------------------------
-- Entities
------------------------------------------------------------

-- A requirement's verification status, reconciled from the runs that carry its id.
entity Verification {
    requirement: String
    status: verified | failed | untested
    runs: List<TestRun>
}

-- The retained evidence of one release, written apart from the results it bundles.
entity EvidenceBundle {
    output: String
    files: List<String>
    manifest: String
}

------------------------------------------------------------
-- Rules
------------------------------------------------------------

-- Reconcile every requirement of the spec against the tag labels of the executed results.
-- A run claims a requirement only by an Allure tag label of its id (a leading "@" is
-- dropped). Passed verifies; failed or broken fails; skipped, or no run, leaves untested.
rule Verify {
    when: Verify(author, dhf, results)
    ensures:
        for requirement in spec.requirements:
            Verification.created(requirement: requirement, status: status_of(requirement, results))
        VerificationRecorded(dhf: dhf)
}

-- Decide whether the commit may be released.
rule ReleaseGate {
    when: ReleaseGate(manager, dhf, results)
    -- 1. a spec is found
    requires: exists spec
    -- 2. it is read whole: no file Gherkin cannot parse
    requires: spec.problems = []
    -- 3. no scenario without an item id
    requires: spec.unstamped = []
    -- 4. no item id on two scenarios
    requires: spec.duplicates = []
    -- 5. at least one requirement
    requires: spec.requirements != []
    -- 6. every requirement verified: a passing run and no failing one
    requires: for requirement in spec.requirements: status_of(requirement, results) = verified
    -- 7. every Allure result read: one RDM cannot read could hold a failed run
    requires: unreadable(results) = []
    -- 8. every user need addressed by a requirement
    requires: for need in spec.needs: addressed(need)
    -- 9. every risk evaluated, its residual acceptable or accepted (risk/risk.allium)
    requires: risk_findings(dhf, results) = []
    ensures: ReleaseGatePassed(dhf: dhf)
}

-- Write the retained evidence of a release.
rule EvidenceBundle {
    when: EvidenceBundle(manager, dhf, results, output)
    -- 1. the output neither holds the results nor sits inside them
    requires: not overlaps(output, results)
    -- 2. the record has a traceability matrix template to render
    requires: exists dhf.traceability_matrix_template
    ensures:
        EvidenceBundle.created(output: output)
        EvidenceBundleWritten(output: output)
}

------------------------------------------------------------
-- Actor Declarations
------------------------------------------------------------

actor ReleaseManager {
    identified_by: ReleaseManagerAccount where true
}

actor RegulatoryAuthor {
    identified_by: AuthorAccount where true
}

------------------------------------------------------------
-- Surfaces
------------------------------------------------------------

-- A release is blocked until every requirement of the spec is verified by a passing test.
surface ReleaseGateDesk {
    facing manager: ReleaseManager
    context spec: Spec

    provides:
        ReleaseGate(manager, dhf, results)
}

-- Each requirement's verification status is traceable from executed test results.
surface TraceVerification {
    facing author: RegulatoryAuthor
    context spec: Spec

    provides:
        Verify(author, dhf, results)

    @guarantee SpecNeedsReadFromTheirSource
        -- The user needs come from the source the spec's configuration names (each
        -- Feature by default, or an adapter's richer model) and each requirement
        -- addresses the needs that source links it to.

    @guarantee UnreadableResultNeverPasses
        -- A result RDM cannot read is never counted as a pass: it blocks release and
        -- is named; a run whose step failed or broke has failed.

    @guarantee RunLabelledWithTheCommitUnderTest
        -- A run that claims a requirement carries the commit it tested, and a mark
        -- when the working tree had uncommitted changes.

    @guarantee RunRecordsWhoRanItAndWhere
        -- The results of an acceptance run record its executor and its environment.
}

-- A release's evidence (verification data, traceability matrix, verification report)
-- and the device-master-record index can be produced as retained, generated artifacts
-- from the record.
surface ReleaseEvidence {
    facing manager: ReleaseManager
    context spec: Spec

    provides:
        EvidenceBundle(manager, dhf, results, output)

    @guarantee DmrIndexFromFrontmatter
        -- The device-master-record index lists every controlled document from its own
        -- frontmatter.

    @guarantee VerificationReportForAReviewer
        -- The verification report shows someone who did not run the tests what was
        -- tested, where, by whom, and whether the evidence is release-grade.
}
